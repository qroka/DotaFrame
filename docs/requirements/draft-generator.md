# DotaFrame — генератор драфтов Dota 2 (MVP)

**Версия:** 0.1  
**Статус:** включён в план MVP по решению владельца продукта; реализация и UI ещё не выполнены  
**Связанная задача по дизайну:** [Issue #7](https://github.com/qroka/DotaFrame/issues/7)  
**Связанные документы:** [границы MVP](mvp-scope.md), [модель данных](../architecture/data-model.md), [архитектура экранов](../design/screen-architecture.md)

## 1. Цель

Создавать квадратную публикацию **«Драфт Dota 2» 1080 × 1080 px** для **одной карты** выбранной серии BO3/BO5. Публикация показывает две команды, по пять выбранных героев, баны и контекст серии.

Добавление шаблона является изменением ранее согласованного MVP: теперь базовых шаблонов **три** — анонс матча, результат серии и драфт.

## 2. Границы MVP

**Входит:**

- Ручное заполнение драфта без API или подключения к игровому клиенту.
- Выбор серии, номера карты и сторон Radiant / Dire для двух команд.
- Выбор **пяти героев** для каждой команды из справочника `Hero`.
- Отдельные списки заблокированных героев (**Bans**) каждой стороны; число банов не следует жёстко привязывать к одному патчу.
- Предпросмотр квадратного постера; отсутствие портрета отображается нейтральной заглушкой.
- Сохранение неизменяемого снимка всей отображаемой информации в `PosterProject`; экспорт PNG 1080 × 1080 после сохранения.
- Проверка дублей героев среди пиков и банов на одной карте.

**Не входит:**

- Автоматическая загрузка драфтов из Dota 2 / сторонних API.
- Редактирование по фазам Captain's Mode, живая трансляция и таймер драфта.
- Зависимость от текущего порядка пиков и банов в конкретном патче.
- Результат **отдельной** карты и полная статистика этой карты.
- Автоматическое определение Radiant / Dire по данным турнира.

## 3. Поля и минимальная модель

### Hero — справочник героев

`Hero { id, name, portraitAssetId? }`

- Уникальный стабильный ID (например, внутренний ID каталога); отображаемое название.
- Портрет из доступных приложению статических ресурсов или из локальной библиотеки изображений. Не использовать внешние URL как обязательное условие работы MVP.
- До внедрения графики требуется проверка условий использования игровых изображений. При отсутствии портрета нужен placeholder.
- Первый справочник героев может поставляться с приложением как статический набор данных, без отдельной UI-страницы редактирования героев.

### GameDraft — драфт отдельной карты

```json
{
  "id": "draft-1",
  "matchSeriesId": "series-1",
  "mapNumber": 1,
  "radiantTeamId": "team-1",
  "direTeamId": "team-2",
  "picksRadiant": ["hero-1", "hero-2", "hero-3", "hero-4", "hero-5"],
  "picksDire": ["hero-6", "hero-7", "hero-8", "hero-9", "hero-10"],
  "bansRadiant": ["hero-11", "hero-12"],
  "bansDire": ["hero-13", "hero-14"]
}
```

Это условный пример структуры, а не реальный драфт. `matchSeriesId` связывает драфт с серией. `mapNumber` начинается с 1; для BO3 допустимы карты 1–3, для BO5 — 1–5. Стороны выбираются редактором и должны соответствовать двум участникам серии.

Достаточно **одного GameDraft на комбинацию `matchSeriesId + mapNumber`**. Карточка драфта — отдельная сущность с данными карты; её не нужно смешивать с итоговым счётом MatchSeries. Полноценную сущность GameMap со счётом, статистикой и временем игры вводить пока не требуется.

## 4. Проверки

| ID | Требование | Ожидаемый результат |
|---|---|---|
| DRAFT-01 | Выбор карты из выбранной серии | Нельзя выбрать номер вне BO3/BO5 |
| DRAFT-02 | Назначение сторон | Radiant и Dire — разные участники серии |
| DRAFT-03 | Пики | Ровно 5 уникальных героев у каждой стороны перед сохранением финального драфта |
| DRAFT-04 | Баны | Списки поддерживают изменяемое количество героев; данные не обрезаются |
| DRAFT-05 | Уникальность | Герой не повторяется между пиками и банами в пределах одной карты |
| DRAFT-06 | Ресурсы | Портреты героев загружаются либо заменяются нейтральной заглушкой |
| DRAFT-07 | Шаблон | Квадратный предпросмотр и PNG 1080 × 1080 после сохранения |
| DRAFT-08 | История | Изменение GameDraft, Team или Hero не изменяет уже сохранённый PosterProject |
| DRAFT-09 | Локальное сохранение | Восстановление драфта и портретов после перезагрузки браузера |

## 5. Изображение и зафиксированные данные

Для сохранённого постера `templateId = "draft"`, `templateRevision` фиксируется как для двух других шаблонов.

`dataSnapshot` должен содержать имена и **версии логотипов** обеих команд, стороны Radiant/Dire, название турнира, BO, номер карты, упорядоченные пики и баны со **снимками имён и неизменяемых версий портретов героев**, дату сохранения и параметры оформления (отдельно в `styleOptions`).

Не достаточно сохранять только `heroId`: если каталог получит новое изображение или новое имя, старый сохранённый постер должен остаться прежним. Пока снимок использует конкретный `MediaAsset`, его нельзя перезаписывать или удалять.

## 6. Дизайн в Figma

На странице `07 — Poster Templates` сделать третий редактируемый Frame **1080 × 1080** — `DOTA 2 DRAFT`, визуально согласованный с анонсом и результатом.

Обязательные блоки: заголовок, две команды, отдельные ряды по пять пиков, два списка банов, номер карты и турнир. Портреты героев должны оставаться читаемыми в уменьшенном предпросмотре. Отобразить состояния отсутствующего портрета, длинных названий и переменного числа банов.

На странице `03 — Wireframes` добавить состояние генератора «Драфт»: выбор серии и карты, назначение сторон, списки пиков/банов и квадратный предпросмотр. Полноценная отдельная страница героев не требуется.

## 7. Открытые технические вопросы

- Источник и лицензия портретов Dota 2; политика доставки локальных ресурсов.
- Допустимый максимум количества банов с запасом на изменение игровых правил.
- Нужен ли пользовательский порядок пиков и банов; в MVP порядок массивов задаётся вручную и сохраняется.
- Поведение чернового (не заполненного полностью) драфта: можно хранить как GameDraft, но **финальную публикацию** создавать только после валидации 10 пиков.

Это не повод начинать разработку до завершения дизайна. Реализация проверяется в будущем техническом прототипе.
