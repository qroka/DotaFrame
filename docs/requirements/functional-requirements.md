# DotaFrame — функциональные и нефункциональные требования

**Версия:** 0.5  
**Статус:** Черновик на согласование  
**Связанная задача:** [#3](https://github.com/qroka/DotaFrame/issues/3)  
**Основание:** [User Stories](user-stories.md), [концепция](../research/project-brief.md)

## 1. Назначение

Документ фиксирует поведение MVP DotaFrame в проверяемой форме. Требования ниже относятся к первой версии, если не помечены как гипотезы для уточнения.

## 2. Функциональные требования

| ID | Требование | Проверка |
|---|---|---|
| FR-01 | Пользователь может создать матч, выбрав две разные команды из справочника и указав турнир, начало и формат серии. | Создать матч с валидными полями |
| FR-02 | Пользователь может изменять данные MatchSeries на отдельной странице, не изменяя снимки ранее сохранённых публикаций. | Исправить название турнира и счёт в серии, проверить старый постер |
| FR-03 | Пользователь может загрузить логотип команды при создании или изменении записи справочника; шаблоны используют связанный логотип. | Создать команду с изображением и выбрать её для матча |
| FR-04 | Система предлагает фиксированный набор шаблонов «Анонс матча» и «Результат серии». | Переключить шаблон для одного матча |
| FR-05 | Новая публикация предварительно заполняется актуальными данными серии и справочника; при сохранении создаётся независимый снимок всех отображаемых значений. | Создать публикацию, изменить исходные записи и проверить неизменность снимка |
| FR-06 | Пользователь может выбрать готовую тему, акцентный цвет и фон из поддерживаемых шаблоном вариантов; произвольное перемещение и шрифты пользователя не поддерживаются. | Переключить разрешённые параметры и проверить предпросмотр |
| FR-07 | После изменения данных или настроек предпросмотр должен обновляться. | Изменить поле и проверить отображение |
| FR-08 | Для результата серии пользователь может ввести счёт обеих команд. | Ввести корректный финальный счёт |
| FR-09 | Система проверяет обязательные поля и валидность итогового счёта по BO3/BO5, включая недопустимые ничьи и избыточное число побед. | Проверить пустые поля, BO3 3:0 и BO5 3:3 |
| FR-10 | При корректном финальном счёте система однозначно определяет победителя серии. | Проверить результаты, включая разные форматы серии |
| FR-11 | После успешного сохранения PosterProject пользователь может экспортировать PNG 1080 × 1080; повторный экспорт использует снимок и версию шаблона. | Проверить отсутствие экспорта до сохранения, PNG и повторный экспорт |
| FR-12 | Экспортируемый PNG не должен включать кнопки, поля и иные элементы интерфейса генератора. | Сравнить PNG с предпросмотром публикации |
| FR-13 | Пользователь может сохранить проект локально и повторно открыть его в том же браузере. | Перезагрузить страницу и открыть сохранённый матч |
| FR-14 | Ошибки ввода, загрузки изображений, сохранения и экспорта должны сопровождаться понятным сообщением. | Воспроизвести соответствующие ошибочные сценарии |
| FR-15 | Пользователь может создавать и редактировать команды в локальном справочнике. | Создать и изменить команду, повторно открыть её запись |
| FR-16 | Один объект Team может быть выбран участником нескольких серий; матч хранит идентификаторы двух разных команд. | Использовать одну команду в двух матчах без копирования записи |
| FR-17 | Повторное открытие сохранённого матча восстанавливает ссылки на команды; отсутствие изображения допускается. | Перезагрузить страницу и открыть серию с командами из справочника |
| FR-18 | Команда «Сохранить публикацию» фиксирует в PosterProject все отображаемые данные матча и команд, параметры оформления, время сохранения и версию шаблона. | Сохранить анонс и результат и проверить поля снимка |
| FR-19 | Изменение команды, турнира, счёта или времени исходной серии не меняет ранее сохранённые PosterProject; новые публикации используют актуальные значения. | Изменить все перечисленные поля и сравнить старый и новый PNG |
| FR-20 | Версии MediaAsset, использованные в исторических публикациях, нельзя перезаписывать или удалять при смене текущего логотипа. | Заменить логотип и проверить экспорт старого снимка после перезагрузки |
| FR-21 | Создание и редактирование серии выполняется на отдельной странице; после добавления команды из справочника незавершённая форма сохраняет введённые значения. | Открыть форму, частично заполнить, добавить команду, вернуться к заполнению без потери данных |
| FR-22 | До успешного сохранения PosterProject доступен предпросмотр; экспорт PNG выполняется только для сохранённой публикации. | Изменить параметры, проверить блокировку экспорта, сохранить и скачать |

## 3. Предлагаемая модель сущностей

Это **предварительная модель**, не готовая схема базы данных:

| Сущность | Основные поля | Назначение |
|---|---|---|
| Team | id, name, logoAssetId | Одна запись команды может участвовать во многих сериях |
| MediaAsset | id, mimeType, fileName, data (Blob) | Неизменяемая версия файла логотипа |
| MatchSeries | id, teamAId, teamBId, tournamentName, startAt, timezone, format, score, status | Серия с двумя ссылками на Team; турнир пока текстом |
| PosterTemplate | id, title, type, revision, exportSize, editableOptions | Версионируемый предустановленный шаблон (1080 × 1080) |
| PosterProject | id, matchSeriesId, templateId, templateRevision, dataSnapshot, styleOptions, savedAt | Независимая сохранённая публикация со всеми отображаемыми данными |

Для MVP предполагается локальное хранение в браузере без серверной базы данных. Для изображений рассматривается IndexedDB с сохранением Blob; конкретную реализацию проверим на техническом прототипе. Отдельный справочник турниров и сущность карты в MVP не требуются.

Расширенная схема: [модель данных](../architecture/data-model.md).

**Принцип:** данные MatchSeries и Team служат источником для создания новых публикаций. При сохранении **все отображаемые значения** копируются в `PosterProject.dataSnapshot`, а параметры оформления — в `styleOptions`; сохраняются `savedAt` и `templateRevision`. При повторном открытии старый пост **не перечитывает** текущие данные серии или команд. Изменение снимка через создание новой публикации — предлагаемое правило MVP.

## 4. Правила валидации

- Название команды в справочнике и название турнира обязательны; серия должна ссылаться на две разные существующие команды. Совпадения названий команд требуют проверки на дубли.
- Дата и время должны быть валидны; часовой пояс нельзя без объяснения выводить из настроек другого пользователя.
- Итоговый счёт — пара неотрицательных целых чисел.
- MVP поддерживает стандартные BO3 и BO5: для BO3 финальный счёт 2:0/2:1 (или зеркальный), для BO5 — 3:0/3:1/3:2 (или зеркальный). BO1, ничьи и технические результаты не входят в MVP.
- Изображение должно корректно обрабатываться при допустимом формате и размере файла; пороги будут определены после технической проверки.
- Для длинных названий и отсутствующих логотипов необходимо предусмотреть безопасный вариант отображения.
- Ошибочные данные не должны незаметно попадать в итоговый PNG.
- Изменение или удаление записи команды не должно приводить к появлению битых ссылок на команду в сохранённых сериях.
- При смене логотипа необходимо создавать новый MediaAsset, а не перезаписывать файл, на который ссылаются исторические снимки.
- Сохранение публикации должно фиксировать название турнира, время начала и часовой пояс, формат и счёт (если они выводятся), а также имена и версии логотипов участников.
- Для воспроизводимости сохранённых изображений нужно учитывать изменение версий шаблонов и используемых ресурсов.
- Отсутствующая текущая запись Team не должна автоматически изменять сохранённые названия в PosterProject.

## 5. Нефункциональные требования

| ID | Требование | Способ проверки |
|---|---|---|
| NFR-01 | MVP работает в настольном современном браузере без отдельной программы. | Открыть и пройти основной сценарий в выбранных браузерах |
| NFR-02 | Для базовых функций не требуется регистрация или платный API. | Пройти сценарий без аккаунта и внешнего API |
| NFR-03 | Предпросмотр и экспорт используют одну модель данных и компоновки. | Сопоставить видимые тексты, изображения и расположение |
| NFR-04 | Экспорт обоих шаблонов MVP имеет фиксированный квадратный размер 1080 × 1080 пикселей (1:1); интерфейс предпросмотра может масштабироваться, не изменяя экспорт. | Проверить размеры обоих PNG и соответствие пропорций предпросмотру |
| NFR-05 | Данные остаются локальными в MVP; политика сохранения и ограничения браузерного хранилища объясняются. | Проверить восстановление и предупреждение о потере данных |
| NFR-06 | Сбой экспорта или сохранения не должен уничтожать уже сохранённые данные. | Смоделировать ошибку и повторно открыть проект |
| NFR-07 | В интерфейсе должны быть видимые подписи полей, понятные сообщения об ошибках и доступное управление с клавиатуры в базовом сценарии. | Ручное UX- и accessibility-тестирование |

**Проверки:** основной настольный набор — актуальные Chrome и Firefox, дополнительно Edge. Размер логотипа, безопасные отступы, перенос длинных названий и целевое время генерации определяются техническим прототипом и wireframes. Экспортное разрешение MVP **1080 × 1080 пикселей**.

## 6. Не включено в MVP

Автоматическая загрузка матчей и драфтов, live-обновления, свободное перемещение/масштабирование объектов, создание произвольных шаблонов, облачная синхронизация, авторизация, публикация в соцсети напрямую, пакетная генерация.

## 7. Ключевые риски

- Экспорт HTML в PNG может некорректно работать со сторонними изображениями, шрифтами и отдельными CSS-эффектами.
- Браузер может ограничить объём хранилища или удалить локальные данные.
- Использование логотипов команд и игровых материалов требует проверки условий и прав.
- Усложнение интерфейса настройки шаблонов может нивелировать выигрыш во времени.
